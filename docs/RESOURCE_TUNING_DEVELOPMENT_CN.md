## 1. 目标与边界

本功能专门面向 **CodeAPI 运行在 Docker 容器中**的部署：包括本仓库 Docker Compose、一键部署生成的 Compose，以及独立 `docker run`。PostgreSQL/Redis 可以是同一 Docker 主机上的容器，也可以是外部服务；它们的资源范围必须分别标识，不能假定共用同一主机或内存预算。

**不支持**以裸机/systemd 运行的 CodeAPI、Kubernetes 等编排环境或非 Docker 容器运行时；这些不是首期分析、应用或验收目标。不能可靠识别是否为支持的 Docker 环境时，显示“部署环境未知”，停止生成可应用方案，不将未知环境误判为支持。部署者声明只作为辅助信息，不能单独证明写入路径、持久化挂载和单实例条件安全。

不同用户的 CPU、内存、Docker 容器限制、请求规模和数据库部署方式不同。固定的大连接池可能浪费资源，过小则可能增加等待。但**硬件规格不能单独决定最佳连接数**：SQL 耗时、突发流量、其他数据库客户端和实例数量同样重要。

首期提供管理员页面，完成以下闭环：

1. 只读采集当前实例及其依赖的可获得信息。
2. 结合近期真实负载，给出有证据的建议或明确显示“数据不足”。
3. 对每个建议展示当前值、目标值、依据、风险和生效方式。
4. 管理员显式选择并确认后，保存**待生效配置**；由管理员按 Docker 部署方式执行重启或重建。
5. 服务启动后核对实际生效值；观察效果，并允许管理员确认恢复上一版本。

### 首期可调整范围

| 对象 | 参数 | 首期处理 |
|---|---|---|
| 应用 → PostgreSQL | `database.max_open_conns`、`database.max_idle_conns` | 允许生成建议与确认保存；不能超过经过确认的数据库预算 |
| 应用 → Redis | `redis.pool_size`、`redis.min_idle_conns` | 允许生成建议与确认保存；明确 `pool_size` 不是硬上限 |
| PostgreSQL 服务端 | `max_connections`、内存参数等 | 只读诊断，不修改 |
| Redis 服务端 | `maxclients`、内存与持久化参数等 | 只读诊断，不修改 |
| 上游 HTTP/WS 池、账号/用户并发、网关调度 | 各自连接与并发参数 | 只解释现状，不提供调整建议或写入 |

不主动压测、不调用付费上游接口、不调整计费/鉴权/限流/审计规则，不修改固定 8080 端口或 portguard。数据库和 Redis 是外部托管时，不假定有管理权限。

## 2. 现有代码与事实

| 能力 | 当前实现 | 设计含义 |
|---|---|---|
| 应用数据库池 | 启动时通过 `database/sql` 设置，见 [`db_pool.go`](../backend/internal/repository/db_pool.go) 和 [`ent.go`](../backend/internal/repository/ent.go) | 现有配置不是管理页面的动态设置；不能将“保存”直接描述为“已生效” |
| 应用 Redis 池 | 启动时创建客户端，见 [`redis.go`](../backend/internal/repository/redis.go) | 首期采用重启生效，不在运行中替换共享客户端 |
| 资源指标 | [`ops_metrics_collector.go`](../backend/internal/service/ops_metrics_collector.go) 尝试读取 cgroup CPU/内存，缺失时回退主机数据 | 标明来源、范围和采样时间；应用容器数据不能冒充数据库容器或物理宿主机数据 |
| 运维页面 | [`OpsDashboardHeader.vue`](../frontend/src/views/admin/ops/components/OpsDashboardHeader.vue) 展示 CPU、内存及应用侧数据库/Redis 池状态 | 可复用视觉和指标入口，但现有页面不是调优器 |
| 配置来源 | [`config.go`](../backend/internal/config/config.go) 读取环境变量、YAML 与代码默认值 | 环境变量可能覆盖 YAML；必须明确标注来源与优先级 |
| Compose 差异 | [`docker-compose.yml`](../deploy/docker-compose.yml) 将部分 `POSTGRES_*` 值传给服务端；[`docker-compose.local.yml`](../deploy/docker-compose.local.yml) 没有相应 PostgreSQL 启动参数 | `.env` 中有值不等于服务端实际已生效；以只读查询结果为准 |

已核实的默认值示例：代码默认 PostgreSQL 池 `256/128`（最大打开/最大空闲）、Redis `1024/128`（基础池/最小空闲）；常用 Compose 的应用侧回退值分别为 PostgreSQL `50/10`、Redis `1024/10`。实际值还受 `.env`、运行环境和部署方式影响，**不可把这些数字当成用户当前运行值**。

当前 `github.com/redis/go-redis/v9` 的 `PoolSize` 是基础连接池大小，不是 `MaxActiveConns` 硬上限；现有代码未设置后者。页面不得把 `redis_pool_size` 标为“最大连接硬限制”。`db_conn_waiting` 虽有字段，当前采集器未填充；现有全局运维采集还采用 leader 机制，不能直接推断全部副本的总和。

## 3. 页面与用户流程

建议入口：管理员「运维监控」下新增**资源调优**，不改变现有运维总览。页面与接口均只对管理员开放。

### 3.1 页面内容

1. **Docker 环境概况**：当前实例标识、部署方式（Compose、独立 `docker run` 或未知）、容器有效 CPU 与内存限制、数据来源与时间；不显示敏感环境变量。
2. **依赖概况**：PostgreSQL/Redis 的连接状态、能读取的服务端上限及占用；权限不足或外部服务未知时明确标“未知”。
3. **观察期**：展示采样时间、有效样本数、近期真实负载、连接池活跃/空闲、等待及错误。运维监控关闭、数据过期或样本不足时显示原因，不填零冒充测量值。
4. **分析结果**：每项标为“保持现状 / 可建议调整 / 数据不足 / 不支持自动应用”。展示证据、目标值、边界、预期收益与可能风险；不承诺性能一定提升。
5. **变更预览与确认**：逐项勾选；显示当前生效值、当前配置来源、目标值、持久化目标、覆盖关系、受影响服务、需重启与回滚方式。任何默认不勾选的项目不得随其他项被改写。
6. **变更记录**：展示版本、操作者、时间、执行阶段、重启要求、验证结果与失败原因，不展示凭据。

只读分析按钮允许重复使用；**不得因打开页面、采样、生成建议或预览而修改任何运行配置**。从预览到确认前若配置、实例身份、依赖容量或方案版本发生变化，必须作废预览并重新分析。

### 3.2 状态与措辞

| 状态 | 含义及页面行为 |
|---|---|
| `insufficient_data` | 采样不足、权限不足、实例/容量不明；只解释原因，禁止声称已优化 |
| `preview_ready` | 只读方案已生成，尚未写配置 |
| `pending_restart` | 管理员确认且待生效版本已安全持久化；当前进程仍使用旧值 |
| `verifying` | 重启后正在核对当前实例及依赖状态；不能直接当作成功 |
| `applied` | 新实例确认读取了对应版本，实际应用池参数和健康检查满足要求 |
| `failed` / `not_applied` | 写入、重启、读取、配置优先级或依赖验证失败；显示旧/实际值与恢复步骤 |
| `rollback_pending` / `rolled_back` | 经管理员确认恢复上一版本；重启并核对后才显示恢复成功 |

网页不得自动执行 Docker/Compose 命令、重启容器，也不得挂载 Docker socket。页面只可提供**与已确认的 Docker 启动方式相符**的人工操作提示；不清楚 Compose 文件、项目目录或 `docker run` 原始参数时，要求管理员按自己的部署记录操作，不生成可能丢失挂载、环境变量或网络配置的重建命令，也不伪造操作已完成。

## 4. 只读采集契约

| 数据 | 来源及范围 | 缺失时 |
|---|---|---|
| 应用 CPU/内存 | 当前 Docker 容器可读取的 cgroup CPU 配额、可用 CPU 集合和内存限制；能可靠确定时取共同约束中的有效限制 | 无有效限制、层级不可见或读取失败时标记未知/回退来源，不把容器可见的值当成数据库容器或物理机规格 |
| PostgreSQL 应用池 | 当前实例 `sql.DB.Stats()`：`MaxOpenConnections`、`OpenConnections`、`InUse`、`Idle`、`WaitCount`、`WaitDuration` | 明确是该实例累计计数/瞬时值，不将 `WaitCount` 冒充当前排队人数 |
| PostgreSQL 服务端 | 在现有连接和权限下只读取得 `max_connections`、可见占用、保留连接；标明查询身份与可见范围 | 托管服务权限受限或共享客户端无法识别时标记未知，不自动提高应用最大连接数 |
| Redis 应用池 | 当前实例 `PoolStats()` 的总/空闲连接和可用的超时、等待统计；单独列出配置的 `PoolSize/MinIdleConns/MaxActiveConns` | 区分基础池与硬上限；不存在硬上限或统计不可得时明示 |
| Redis 服务端 | 在已有权限允许时，只读查询实际 `maxclients`、已连接客户端及必要内存状态；优先低开销只读命令 | ACL 不允许、代理隐藏结果或共享实例不明时标记未知，不要求管理员授予高权限 |
| 负载 | 真实请求 QPS、延迟/错误、池等待增量，按实例与时间窗关联 | 无流量、采样中断或新部署时保持现状，不产生臆测 |

采集为低频、受超时和成本限制的只读操作。原始输出不得包含 API Key、令牌、密码、连接串或其他客户端的敏感信息。服务端可见性受账号权限、代理和托管产品限制，结果必须带**来源、采集时间、实例标识、完整性/置信度**。

Docker Desktop 在 macOS/Windows 上通常通过 Linux 虚拟机运行容器：容器看到的主机指标可能是虚拟机指标，不等于物理机规格。容器未设置资源限制时，cgroup 可能显示无限额；不得将回退结果标为“Docker 实际独占资源”。普通容器仅凭自身视角不能可靠取得同主机 PostgreSQL/Redis 容器的 CPU、内存限制或 Docker Desktop 全局分配，缺失即标“未知”，不为采集新增 Docker socket、特权容器或宿主目录挂载。

Docker 身份识别应采用保守策略；单一标记文件、cgroup 名称或前端声明不构成可靠证明。实现前需明确证据来源与可信度；不可判定或与 Kubernetes/其他运行时冲突时按“不支持自动应用”处理。

## 5. 推荐逻辑（待确认的首版规则）

### 5.1 前提与观察窗口

- 以自然流量为依据，不新建压测请求。建议观察 **24 小时**并包含用户业务高峰；窗口不足时标记低置信度，默认只展示诊断，不生成可应用数值。
- 采样间隔建议 60 秒；记录实例启动标识与时间戳。重启后的累计计数不能直接与旧进程相减，缺样、计数回退、时钟异常的区间排除。
- 必须同时看峰值及 P95 活跃连接、等待次数/时长的**区间增量**、请求量、错误与延迟趋势。空闲连接多不等于池过大；单次高峰也不足以扩大连接池。
- 初版阈值和百分位作为**设计候选，不是实测最优值**。在合成负载和受控环境验证前，不根据 CPU/内存公式直接生成固定推荐档位。

### 5.2 PostgreSQL

1. 先确定应用池当前配置及其生效来源，再只读查询数据库服务端实际限制。
2. 明确数据库保留连接、管理员运维余量、其他应用/客户端使用与**其他副本的最大连接预算**；不能把当前已使用数同时算作当前实例预算，否则会重复扣除。
3. 可用于本实例的上限应满足：

   `本实例预算 ≤ 服务端实际上限 − 服务端保留 − 运维余量 − 其他客户端及其他副本预留预算`

   左右两边必须使用同一数据库服务端、同一时点和明确的统计口径；其他客户端/未来副本预算未知时不建议增加最大值。共享数据库和多副本若无法证明预算完整，**只读展示并阻止自动应用增加值**。
4. 观察期内存在持续等待且数据库还有确认过的预算时，才可提出有限幅度的上调候选；低负载且峰值/等待有足够证据时，才可提出下调候选。变化幅度、冷却期与上下边界须在实现前用测试与基准确定，不硬编码为“硬件越大连接越多”。
5. 始终满足 `max_open_conns > 0`、`0 ≤ max_idle_conns ≤ max_open_conns`。已有校验见 [`config.go`](../backend/internal/config/config.go#L3137)；首期不改生命周期/空闲超时，以免改变连接故障恢复语义。

示例：数据库实际允许 100 条，服务端保留和运维余量合计 15 条，其他客户端及其他副本已确认预留 35 条，则本实例预算最多为 `100 - 15 - 35 = 50`；这只是**容量上界**，不是推荐立即设置为 50。

### 5.3 Redis

1. 分开显示应用侧 `PoolSize`、`MinIdleConns`、可能的 `MaxActiveConns`，以及服务端实际 `maxclients` 和客户端占用；不得以 `PoolSize` 作为硬上限计算保障。
2. `MinIdleConns` 偏高可能持续占用连接和内存，但调低可能增加冷启动建连延迟。仅在有足够长期低负载证据、无明显建连/等待问题时提出候选。
3. 连接等待或超时增加不必然说明池太小，也可能是 Redis 服务端、网络或慢操作。先诊断依赖健康；服务端容量/其他客户端未知时不建议提高连接预算。
4. 现有校验要求 `pool_size > 0`、`0 ≤ min_idle_conns ≤ pool_size`。首期不悄悄引入硬上限；如将来引入 `MaxActiveConns`，须单独设计、回归和确认。

### 5.4 安全规则

- 未知不等于零；权限错误、不可用、数据过期、样本不足均需显示“未知/不足”。
- 推荐不跨越已知服务端预算，不默认覆盖管理员既有设置；同值不生成变更。
- 不因短时 CPU 高或内存高就直接缩小连接池；如果依赖状态异常或指标相互矛盾，停止数值推荐并展示诊断。
- 任何建议都要可追溯：规则版本、观测窗口、样本质量、输入摘要、计算过程、边界与预计重启影响。

## 6. 确认应用与配置优先级

### 6.1 推荐实现：显式托管的应用池覆盖文件

现有环境变量通常优先于 YAML，而应用启动前还不能依赖数据库中的设置来初始化数据库连接池。因此建议首期使用**独立的、仅包含四个允许参数的托管覆盖文件**，存放在 Docker 部署中由管理员确认的应用持久化数据挂载；不覆盖 `config.yaml`、`.env` 或 Compose 文件，不记录秘密。

- 默认关闭托管覆盖；仅部署者通过明确的启动配置启用后，页面才允许“确认保存待生效配置”。部署者未启用、目录只读或持久化能力不可确认时，只提供建议和供人工修改的参数清单。
- 启用托管覆盖时，**仅这四个允许参数**的优先级拟定为：经管理员确认的有效托管版本 > 环境变量 > YAML > 代码默认值；其他配置保持现有优先级。页面必须同时显示被覆盖来源和值，并在首次启用托管时要求明确确认接管。
- 仅允许固定文件名与四个整数键；拒绝未知键、路径/符号链接越界、无效范围与不匹配版本。每次只更新管理员勾选的键，未勾选的既有托管值必须原样保留；撤销某一键的托管、回到环境变量/YAML 时也需单独预览确认。文件权限最小化，使用同目录临时文件、校验和原子替换；并发确认使用版本号和条件写入，避免覆盖运维人员修改。
- 确认时保存带版本的**待生效方案**和上一已确认版本；不在当前进程内热替换 Redis 客户端，不自动退出进程。页面提供管理员可复制的、适配其部署的重启步骤。
- 新进程启动前必须完整校验候选；加载失败不能覆盖上一有效版本。启动后核对配置来源、候选版本、实际 `sql.DB.Stats().MaxOpenConnections` 与 Redis 客户端选项，并标记结果。数据库连接或启动失败时，不能依靠已经失联的应用页面宣称自动回滚；必须提供可在应用不可用时由运维人员执行的文件级恢复步骤。
- 如重启后托管功能被禁用或文件未加载而使环境变量重新生效、挂载不持久、文件被外部改动，或预览时无法验证持久化路径，状态必须为 `not_applied` 或 `failed`，不能标“成功”。禁止在重启前把 pending 值展示为生效值。

该覆盖优先级是**拟新增设计**，并非现有行为。具体启动配置键、文件格式、版本保留数量和失败恢复方式应在用户确认后实现并用故障注入验证；不得通过向应用挂载 Docker socket 解决重启问题。

### 6.2 Docker 部署适配

| 场景 | 可分析 | 确认后可自动持久化 | 生效方式 |
|---|---|---|---|
| 单实例 Compose，持久化挂载可确认且显式开启托管 | 本容器 + 可读依赖 | 四个应用池参数，写托管版本 | 管理员按原 Compose 部署方式重启/重建应用；重启后核对 |
| 单实例 `docker run`，持久化挂载可确认且显式开启托管 | 本容器 + 可读依赖 | 四个应用池参数，写托管版本 | 管理员使用原有容器创建参数操作；重启后核对 |
| Docker 容器未开启托管或持久化挂载不可确认 | 本容器 + 可读依赖 | 不覆盖 `.env`、Compose 或容器配置 | 只输出人工修改建议，不自动重启 |
| Docker 中的 CodeAPI 连接外部 PostgreSQL/Redis | 本容器 + 现有权限可读部分 | 满足单实例托管条件时只写本应用参数 | 不修改外部服务端参数 |
| Docker 多副本、多主机或共享依赖预算不明 | 每实例只读信息，需识别实例来源 | **首期不支持自动写入** | 显示限制和人工协调指引；不把单实例指标当集群总量 |
| 裸机/systemd、Kubernetes、其他运行时或 Docker 身份无法确认 | **不在功能支持范围** | 不支持 | 不提供自动应用；提示当前环境不支持或无法确认 |

优先保证分析与预览可用；写入能力不可用时，页面应说明为什么以及管理员如何手动应用，不能假装完成。

## 7. 安全、审计和异常处理

- 管理员认证、现有限流和管理审计不削弱；保存与回滚属于敏感写操作，复用项目现有 step-up 机制及开关语义，失败时拒绝写入。
- 服务端重新计算并校验白名单参数，不信任前端传来的建议数值、预算、实例数或配置路径。确认请求携带方案版本和有效期；过期、并发修改或容量变化则拒绝并要求重新预览。
- 审计记录操作者、实例/部署范围、规则版本、前后数值、操作结果和失败原因；禁止记录密码、令牌、完整环境变量或数据库连接串。
- 数据库/Redis 超时、权限不足、池耗尽、文件系统只读、空间不足、原子写失败、重启中断、配置冲突和恢复失败均必须有可见错误；失败不能部分写入其他选项。
- 在服务启动前执行现有 `Config.Validate()`，保留固定端口、鉴权、限流、计费一致性和审计护栏。对故障恢复设计进行断电/进程退出注入测试。

## 8. 拟议实现切分

以下路径和 API 为候选，不表示已经存在；具体名称以实现时项目结构为准。

1. **只读采集与契约**：独立 service/repository 采集实例资源、池统计、依赖容量与来源；补充数据库等待增量、Redis 统计口径，不修改现有网关核心路径。
2. **纯函数分析器**：输入经过验证的快照和观察窗，输出结果、证据、置信度、阻断原因和版本；无 I/O、无配置副作用，便于单测与回放。
3. **管理员预览页面**：优先复用 `frontend/src/views/admin/ops/` 与 `frontend/src/api/admin/ops.ts` 的结构；新增中英文 i18n，不依赖现有 leader 样本推断多实例总量。
4. **确认与受控持久化**：在用户确认本文方案后实现可选托管文件、版本并发控制、启动加载/核对、审计、失败提示和外部恢复；管理员确认与部署者预先启用托管是两道独立门槛。
5. **验证与交付**：先 unit/integration，再在隔离的单实例 Compose 环境检查启动、重启及恢复；不对用户现有生产容器做自动变更。

拟议 API 至少分离只读快照/分析、方案预览、显式确认、状态查询和显式回滚。实现前须固定请求/响应 DTO、错误码、方案过期规则、权限及幂等键；`GET` 和预览不得产生配置副作用。若实现需要暂存预览快照，只允许写入有期限的分析元数据，不得改变运行参数或部署文件。

- 单实例与多实例场景验证 PostgreSQL 预算计算不重复扣除，其他客户端未知时不提出可应用的上调方案；服务端重启/配置改变后旧预览作废。
- 页面显示数据来源、时间、范围、原因、置信度、当前值/建议值、重启影响；i18n 键完整，键盘及移动端操作可用。

- 重启前保持旧运行值；重启后读取到对应版本且实际值一致才标 `applied`。环境覆盖、目录只读、磁盘满、权限错误、文件损坏、启动失败和回滚失败均不得报成功。

- 前端：`pnpm` 的 lint、typecheck、相关组件测试、i18n 检查以及生产构建到 `backend/internal/web/dist`。
- 文档与变更：`git diff --check`、配置来源/敏感信息检查；必要时记录部署兼容变化与人工恢复步骤。

## 10. 待用户确认的决策

1. 首期只调整应用侧 PostgreSQL/Redis 四项池参数；数据库/Redis 服务端及上游 HTTP/WS 池只诊断，不写入。
2. 采用“只读分析 → 预览 → 管理员确认保存待生效方案 → 人工重启 → 实际值验证”的流程，不自动重启容器。

## 11. Docker Compose 动态优化与 1C1G 验证方案（2026-11-04）

### 11.1 目标和约束

+- 部署目标收敛为 Docker Compose：CodeAPI、PostgreSQL、Redis 可能同机，也可能由 Compose 之外提供依赖。优先验证三者同机的 1 核 1 GiB 场景，不自动假定所有部署都同机。
+- “动态”首先指**持续采样、动态刷新诊断和推荐**；不等于后台自行更改生产参数。每次配置变更仍需管理员确认，生效后持续观察。历史申请的“用户确认后开发”仍有效。
+- 配置阈值是控制策略的**待验证候选**，不是已实测的最佳值；未经过可重复的基准与故障验证前，不提供可自动应用的推荐数值，也不承诺 1C1G 可承载的 QPS、用户数或性能折损百分比。
+- 内存预算必须覆盖应用、数据库、Redis、操作系统及页缓存；容器 cgroup 数据只能证明本容器可见范围。Docker Desktop 虚拟机限额、其他容器用量和真正的物理机内存若不可读，明确显示未知；管理员手动输入只是已声明数据，不当作系统实测。
+
+### 11.2 动态运行状态与控制
+
+1. 默认**观察模式**：每 60 秒低成本采集一次（候选值），显示时间、数据来源、采集延迟、覆盖率。持久化指标的保留期与开销须实施前验证；监控关闭时不得暗中开启高开销采集。
+2. 以 15 分钟短窗做告警，24 小时长窗（含业务峰值）做配置建议。短窗不足时只显示实时状态；长窗不完整、低流量、实例重启导致计数器重置时不生成可应用数值。具体最小样本数和覆盖率属于待压测校准项。
+3. 输出四种判定：`保持`、`建议调整`、`数据不足`、`禁止应用`；每条建议附观察数据、原因、计算公式/规则版本、变化范围、预期风险及下一次复核时间。不得将 CPU 高直接映射为增加连接数。
+4. 压力状态候选：内存逼近容器/宿主可确认上限、OOM/重启、计费失败、Redis 或数据库不可用时冻结推荐应用，展示证据及人工处置；恢复需要连续稳定观察和新方案确认。实际阈值通过实验确定，避免引入未经验证的“自动安全值”。
+5. 待实施的控制算法先在影子模式与隔离环境中回放：设定上下界、变更步长、滞回和冷却期，防止短时突发造成频繁扩缩；默认不自动执行。指标缺失、状态冲突、超时或配置来源改变时 fail-closed，保留当前值。
+
+### 11.3 参数与生效路径
+
+| 参数 | 当前事实 | 拟议首版 | 动态生效和恢复 |
+|---|---|---|---|
+| 应用 PostgreSQL 最大打开/最大空闲 | [`applyDBPoolSettings`](../backend/internal/repository/db_pool.go) 仅在启动初始化时调用；`database/sql` 提供运行时 setter | 观察并生成候选；首版沿用第 6 节确认保存、人工重启和实际值核验 | 不默认热改；若以后增加运行时调整，需先设计并发顺序、当前活跃连接收敛、持久化/重启一致性和故障回滚，并单独经过确认与验证 |
+| 应用 Redis 基础池/最小空闲 | [`InitRedis`](../backend/internal/repository/redis.go) 启动时创建共享客户端；`PoolSize` 不是硬上限 | 观察并生成候选，明确基础池与 `MaxActiveConns` 的区别 | 经确认持久化后人工重启；不在请求进行时无验证地替换共享 Redis 客户端 |
+| PostgreSQL/Redis 服务端参数 | Compose 文件与外部托管服务的权限和配置不同 | 首版只读诊断，提示实际值与 Compose 来源不一致 | 不通过页面直接改服务端或自动重启依赖 |
+| 用量记录工作池、队列、并发/限流、上游池 | 影响计费、稳定性或流式连接；代码有现成配置与各自语义 | 只观察，不纳入首版动态调参 | 不切换为 `drop/sample`，不弱化计费、鉴权、限流、审计与 8080 护栏 |
+
+页面同时展示当前运行值、配置来源、建议值和待重启值；不会覆盖 `.env`、Compose 配置、秘密或用户未勾选的参数。第 6 节的托管覆盖方案只是待确认设计，**不意味着已经获得应用或重启授权**。取消/回滚需明确管理员确认；服务无法启动时还要有脱离网页的可执行恢复流程。
+
+### 11.4 建议的 1C1G 对照实验协议
+
+目的：先测清配置和硬件分别造成的影响，再决定哪些动态建议有证据。仅在隔离的测试环境运行，不向真实付费上游发送请求，不改生产实例。
+
+**实验对象与对照**：
+
+- A：同一台 1C1G 机器（或明确标注的等效隔离环境），使用部署实际生效的现有配置；B：相同环境，使用人工审核后的候选配置。只改变要研究的参数，先逐个变量、再组合测试。
+- 硬件对照 C：同硬件架构、存储和网络条件下的 2C2G（若可获得），运行 A 的同版本同配置。若只能用容器限额模拟，标注为模拟，不能声称等同 1C1G 物理机；同一宿主机其他负载须隔离并记录。
+- 所有组固定镜像版本/摘要、代码提交、Compose 文件、内核及 Docker 版本、架构、CPU 配额/绑核、内存/Swap 限制、数据库版本、数据量和账号数、并发模型、持久化/磁盘条件。记录 `docker compose config` 的**脱敏摘要**及依赖实际生效值，禁止保存密码或完整连接串。
+- 模拟上游采用独立主机或隔离资源，提供固定非流式/流式延迟和稳定响应；压测端不得与被测 1C1G 共用资源。固定 token/请求体大小、连接复用、服务时间、响应块间隔、错误比例和流式持续时间。
+
+**负载与重复**：
+
+1. 测启动、健康检查、无流量空载；分别记录冷启动与预热后资源。完整数据库迁移和初始化独立计时，不与稳态 QPS 混算。
+2. 文本非流式和流式分开，覆盖阶梯式低负载、预期业务峰值、短时突发和 30 分钟稳定运行；每档预热 5 分钟、测量 15 分钟，至少重复 3 次并交替 A/B 顺序。若时间或样本不足，报告不完整而非外推结论。
+3. 同时记录压测端**实际发出**的速率和成功/失败/超时；包含排队时间和完成时间，不用只看成功请求的延迟。流式记录首字、完整响应时间、活跃流数、断流和中断后的计费结算。
+4. 测计费完整性：使用隔离数据库与可核对的固定响应，核对成功请求、usage 记录、余额/配额扣减及幂等，不因追求吞吐关闭安全检查或改为丢弃计费。包括 Redis/数据库短时不可用及恢复后的行为，单独报告失败和恢复。
+
+**指标与计算**：
+
+| 指标 | 测量方式 | 判断 |
+|---|---|---|
+| 有效吞吐 | 单位时间内成功且计费/usage 对账一致的请求数；同时公布所有请求数 | 吞吐不是注册用户数；错误请求不能算成功吞吐 |
+| 端到端延迟、P95/P99、首字 | 压测端分别统计全量成功及失败/超时；公布样本量 | 同负载比较；超时比例单列，不靠丢弃超时改善 P99 |
+| CPU | 容器/服务 CPU 使用、限流时间和整机可确认指标，按时间序列观察 | 记录口径和限额；单次满载不等于瓶颈已定位 |
+| 内存 | 三容器与宿主可见内存、cgroup `memory.current/peak/events`、OOM/重启、Swap/主机可用内存 | 统计口径可能重叠，禁止直接求和当整机 RSS；记录限制来源 |
+| 依赖连接 | 应用 DB `Stats` 等待次数/时长增量、Redis `PoolStats` 可获得的连接/超时，以及服务端实际连接余量 | 区分瞬时值和累计量；缺少权限则标未知 |
+| 稳定性与计费 | 非 2xx/5xx、超时、流式断开、usage 与账目差异、容器重启/OOM | 任何计费缺失或重复必须视为失败，不用性能指标掩盖 |
+
+对同一指定负载的指标，分别报告每次结果、中位数和波动范围：吞吐折损 `（基准吞吐 − 测试吞吐）/ 基准吞吐 × 100%`；延迟变化 `（测试延迟 − 基准延迟）/ 基准延迟 × 100%`。基准为零、样本太少或组间硬件/负载不一致时不计算百分比。另按预先约定的错误率和 P95/P99 目标求最大稳定负载；不能用不同错误率下的峰值吞吐直接比较。
+
+### 11.5 验收、报告和上线顺序
+
+- 在实验前由管理员确认目标业务负载、延迟与错误率预算；不能事后选阈值使方案看似通过。基础门槛：零新增计费不一致、零 OOM/非预期重启，鉴权、限流和审计行为不弱化；性能目标需根据业务约定，不预设虚构数字。
+- 输出测试报告：环境与版本、数据量、负载模型、原配置/候选配置、实际生效值、样本量、每次数据与波动、失败与不确定性，以及是否达到事先设定的目标。仅凭本地开发机或 Go microbenchmark 不得声称得出 1C1G 生产容量。
+- 顺序：① 只读诊断与观测采集 → ② 在隔离 Compose 验证推荐 → ③ 管理员确认后应用待重启配置 → ④ 重启验证及效果观察。未经独立确认和故障测试，不上线无人值守闭环调参。
+- 若希望获得**当前部署的真实数字**，需取得该服务器 Compose 启动方式、实际资源配额、数据库/Redis 是否同机、自然业务高峰、可接受的测试窗口及对照环境；敏感值不收集。
